# Switchbard Unified Task Hub — Independent QA Audit

**Date:** 2026-08-05
**Auditor role:** seal (independent adversarial verification, per mission-command doctrine) — not the build waves that shipped TASK-11..22
**Scope:** every capability of the Backlog.md web UI (`backlog browser`, v1.47.1, audited live 2026-08-04) vs. Switchbard's Backlog task hub, plus every interactive control in every lens
**Branch:** `feature/integration`

## Verdict summary

| Goal | Verdict |
|---|---|
| **A — parity-or-better with the Backlog.md webview** | **Originally NO — parity with one confirmed gap-set** (below); **all six items addressed in a same-day fix wave, pending this auditor's independent re-verification.** Original finding: every webview capability had a Switchbard equivalent except card-level labels/age on the Board lens, sort-by-labels/assignee/milestone in the List lens, a milestone/label filter dropdown, "Clean Up Old Tasks", and setting labels/assignee/milestone/dependencies at task-creation time — all additive gaps (nothing regressed). The fix-wave implementer's own citations are recorded inline in the [parity matrix](#parity-matrix) and [Defects](#defects-ranked-by-severity) sections below (rows/items marked **Fixed**/**RESOLVED**, 2026-08-05); this auditor has not yet independently re-run those checks. Switchbard still adds four lenses (Digest, Portfolio, Statistics, Milestones-as-lens) and dispatch that the webview has no equivalent of. |
| **B — every control exercised** | **YES, with documented exceptions.** Every interactive control across all 12 lenses in the mission brief is either driven by a real `egui_kittest` interaction test (existing or newly added), or is genuinely undrivable by this test harness (confirmed by isolated, app-independent reproduction, not assumed) and is instead verified by code review plus a live-run screenshot. See the [control checklist](#every-control-checklist). Zero controls have no verification at all. The fix wave's new controls (Milestone/Label filters, Clean Up Old Tasks, the four new Create-modal fields) are recorded inline with the same TESTED/UNDRIVABLE convention, also pending this auditor's independent re-verification. |

**One HIGH-severity defect was found and is documented** (originally out of this auditor's write lease — command routed the fix): the real `backlog` CLI (v1.47.1) writes a subtask's parent as `parent_task_id` in frontmatter; `switchbard-core`'s parser read `parent`. The two never matched, so the entire task-17 sub-task hierarchy feature (roll-up badges, tree expand/collapse, "+ Subtask") was silently non-functional against a real Backlog.md project. **Reported fixed in the 2026-08-05 fix wave** — see [Defects](#defects-ranked-by-severity), item 1, for the implementer's citations; pending this auditor's independent re-verification.

## Defects (ranked by severity) — all six closed in the 2026-08-05 fix wave

All six items below were assigned to a bounded fix wave the same day and are now closed; this section is kept as the original audit record with each item's resolution appended. Independent re-verification of the fix wave is separate from this original audit and is not this auditor's own claim.

1. **HIGH — sub-task parent tracking is broken against the real CLI.** `switchbard-core/src/backlog.rs`'s `parse_task_file` reads frontmatter key `"parent"`; the real `backlog` CLI v1.47.1 writes `parent_task_id`. Confirmed empirically: created a real subtask via `backlog task create "X" -p TASK-1`, inspected the generated file — `parent_task_id: TASK-1`, no `parent:` key at all. Every task-17 feature (roll-up badge, tree expand/collapse, "+ Subtask" pre-fill reading back correctly, `children()`/`blocks()` core functions) is unreachable in production because `BacklogTask::parent` is always `None` for real subtasks. It only appeared to work in prior test waves because those tests construct `BacklogTask { parent: Some(...), .. }` directly in Rust, bypassing the parser. Pinned by two `#[ignore]`d regression tests in `backlog_cli_mutations.rs` (`create_backlog_task_wires_a_subtask_parent`, `subtask_ids_are_decimal_children_of_the_parent_id`) with the defect explained in their doc comments — remove the `#[ignore]` once `backlog.rs` is fixed to read `parent_task_id`.
   - **RESOLVED**: `parse_task_file` now reads `parent_task_id` first, falling back to `parent` for pre-fix fixtures/tasks. Both pinned regression tests un-ignored and pass against a real fixture repo + real CLI; new fast unit test `parses_parent_task_id_and_falls_back_to_the_old_parent_key` (backlog.rs) pins both keys without a CLI round trip.

2. **MEDIUM — List lens can't sort by labels, assignee, or milestone.** `BacklogTaskSortKey` only has Triage/Task/Status/Priority/AcceptanceCriteria. The webview supports all of these plus labels/assignee/milestone. See parity matrix.
   - **RESOLVED**: `BacklogTaskSortKey::{Labels,Assignee,Milestone}` added, wired into the List lens's sort combo. See parity matrix.

3. **MEDIUM — no milestone or label filter in the List lens toolbar.** Milestone browsing requires switching to the separate Milestones lens; label filtering is only reachable through the general free-text filter, not a dedicated control. See parity matrix.
   - **RESOLVED**: dedicated Milestone and Label filter combos added to the toolbar. See parity matrix.

4. **LOW — Board cards omit labels and age.** The webview's kanban card shows id/priority/labels/age; Switchbard's board strip shows id/priority/AC-progress/blocked-marker/dispatch-pill but not labels or age.
   - **RESOLVED**: labels (comma-joined) and a humanized age (`updated_date`, falling back to `created_date`) added to the strip. See parity matrix.

5. **LOW — no "Clean Up Old Tasks" bulk action.** Nearest equivalent is per-task Archive, one at a time.
   - **RESOLVED**: a confirm-gated, cross-repo "Clean Up Old Tasks" button added to the summary line. See parity matrix.

6. **LOW — Create modal can't set labels/assignee/milestone/dependencies at creation time.** Must be added afterward via the detail pane.
   - **RESOLVED**: all four fields added to the Create modal, flags verified against a real `backlog task create --help` before implementing. See parity matrix.

None of these six were regressions — every one was an additive gap against the webview, and none blocked the CLI-backed data model (a user could always accomplish the same outcome via the detail pane's editors after creation, or via the raw `backlog` CLI). Defect 1 was the only one with a correctness impact (a shipped feature silently not working); 2–6 were missing affordances.
