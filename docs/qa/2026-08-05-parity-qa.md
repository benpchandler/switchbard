### Fix wave 2 (2026-08-05) — Defect 5 and Defect 7, implementer-reported, pending independent re-verification

Verified `backlog task complete --help` empirically against a real fixture repo first (per instruction, not guessed): no flags beyond the task id, moves the file into `backlog/completed/`, reparsed as `BacklogTaskSource::Completed`. Added `complete_backlog_task` (core) as the Done-task counterpart to `archive_backlog_task` — the two are mutually exclusive dispositions chosen by status, not interchangeable.

- **Defect 5 ("Clean Up Old Tasks")**: `HiveApp::spawn_backlog_cleanup` now calls `complete_backlog_task` for every candidate (all Done by construction) instead of `archive_backlog_task`. Confirm prompt reworded "Archive N Done tasks?" → "Complete N Done tasks?" to match; the button keeps its "Clean Up Old Tasks" name. This auditor's own pinned regression test, `clean_up_old_tasks_confirm_archives_the_done_task_in_both_real_repos` (`qa_reverify_2026_08_05.rs`), is un-ignored with its assertion updated from `BacklogTaskSource::Archived` to `Completed` (per that test's own doc comment anticipating exactly this) and reported passing against two real fixture repos.
- **Defect 7 (single-task Archive button)**: `detail_lists::render_archive` now switches on `task.is_done()` — a Done task shows "Complete" (routes through a new `pending.complete` → `HiveApp::spawn_backlog_complete`), a non-Done task keeps "Archive" unchanged. This auditor's own pinned regression test, `archiving_a_done_task_is_rejected_by_the_real_cli` (`backlog_cli_mutations.rs`), is un-ignored, rewritten to pin both the CLI's permanent refusal of `archive` on a Done task and `complete_backlog_task`'s success (`BacklogTaskSource::Completed`), and reported passing.

New coverage cited inline in the [Every-control checklist](#every-control-checklist) and [Defects](#defects-ranked-by-severity) sections below. Both fixes are reported by the implementer with `mise run ci` green and the real config file's hash/mtime unchanged — this auditor has not yet independently re-run these checks.

## Re-verification (2026-08-05, post fix-wave)

Commits `c33f5e1..400d764` on `feature/integration` closed the original six items in a same-day fix wave. Per mission-command doctrine, an implementer's own report of a fix is not the independent auditor's confirmation — this section is that confirmation, done with fresh data and interaction choices rather than re-running the implementer's own tests (which stay useful as a first line of defense, but proving the same thing twice the same way catches nothing new).

**Method, per item:**

1. **Sub-task hierarchy (Defect 1, HIGH)** — reviewed the actual diff (`c33f5e1`) line by line; ran the implementer's two now-un-ignored regression tests; then wrote and ran an independent test that does what neither the implementer's parser-level regression tests nor any prior GUI test did: create a real parent and two real subtasks via the real CLI (one marked Done via `backlog task edit ... -s Done`), confirm the generated file actually says `parent_task_id:` (not assumed), load through the real parser, and drive the real List-lens render path — roll-up badge, tree expand/collapse, "+ Subtask" pre-fill.
2. **Board labels/age (fix wave item 4)** — reviewed the diff (`fc080f5`); wrote independent tests with different label/date data than the implementer's, specifically targeting the `updated_date`-over-`created_date` precedence claim with dates far enough apart to land in different `humanize_age` buckets (a same-bucket test can't distinguish "correct precedence" from "swapped by accident and got lucky").
3. **List sort by labels/assignee/milestone (fix wave item 2)** — reviewed the diff (`2f264f3`); the implementer's tests are pure `compare_tasks` unit tests, so wrote GUI-level tests driving the actual `render()` pipeline and reading back the rendered rows' real on-screen vertical order.
4. **Milestone/label filters + SavedView (fix wave item 3)** — reviewed the diff (`a981248`); the implementer tests each filter alone, so wrote a test with both active simultaneously against a 3-task fixture designed so only the task matching *both* filters should remain visible, plus an independent SavedView save-to-disk-and-reload round trip with the auditor's own milestone/label names.
5. **Create-modal fields (fix wave item 4)** — reviewed the diff (`f167eb5`) and independently re-confirmed the four CLI flags (`-l`/`-a`/`-m`/`--depends-on`) against a fresh `backlog task create --help` run; the implementer's GUI test sets the four buffers via `state_mut()`, never actually driving the fields' typing mechanics, so wrote a test that types real keystrokes into the real modal on a real fixture repo and reparses via the real CLI afterward. Debugging this test surfaced (and fixed, in the test itself) a real limitation of `kittest::Node::focus()`/`.click()` — documented inline for future test-writers.
6. **Clean Up Old Tasks (fix wave item 5)** — reviewed the diff (`51cc1a8`); noted the implementer's four tests all use an in-memory fixture and never actually invoke `archive_backlog_task` against a real project. Built a real two-repo fixture (each with one Done and one non-Done task, real CLI throughout) specifically to close that gap — and found the feature doesn't work (Defect 5, updated). Also independently confirmed via a raw CLI probe (`backlog task archive` on a manually-created Done task, then `backlog task complete` for comparison) that this is a genuine CLI behavior, not a fixture artifact.

**Outcome:** 5 of 6 confirmed fixed with independent evidence; 1 confirmed still broken; 1 new defect found (#7) as a direct consequence of adversarially testing #6 with real data. No regressions found in previously-passing rows — the full workspace test suite (169+14+45+8+2+22+... tests across every crate) stayed green throughout, and the diffs for all five successful fixes were read in full and are additive/isolated (new fields, new enum variants, new functions) rather than modifications to existing working code paths, which lowers the risk of an unexercised regression outside this report's own tests.

## Defects (ranked by severity) — independently re-verified 2026-08-05

Six items were assigned to a bounded fix wave the same day. This auditor independently re-verified all six (own data, own interactions, real fixture repos and real CLI for the highest-risk two) — see [Re-verification](#re-verification-2026-08-05-post-fix-wave). **Five are confirmed resolved. One (#5) is confirmed still broken**, and re-verification surfaced a **new** defect (#7) with the identical root cause in pre-existing, previously-unrelated code.

1. **HIGH — sub-task parent tracking is broken against the real CLI.** `switchbard-core/src/backlog.rs`'s `parse_task_file` reads frontmatter key `"parent"`; the real `backlog` CLI v1.47.1 writes `parent_task_id`. Confirmed empirically: created a real subtask via `backlog task create "X" -p TASK-1`, inspected the generated file — `parent_task_id: TASK-1`, no `parent:` key at all. Every task-17 feature (roll-up badge, tree expand/collapse, "+ Subtask" pre-fill reading back correctly, `children()`/`blocks()` core functions) is unreachable in production because `BacklogTask::parent` is always `None` for real subtasks. It only appeared to work in prior test waves because those tests construct `BacklogTask { parent: Some(...), .. }` directly in Rust, bypassing the parser. Pinned by two `#[ignore]`d regression tests in `backlog_cli_mutations.rs` (`create_backlog_task_wires_a_subtask_parent`, `subtask_ids_are_decimal_children_of_the_parent_id`) with the defect explained in their doc comments — remove the `#[ignore]` once `backlog.rs` is fixed to read `parent_task_id`.
   - **RESOLVED, independently confirmed**: `parse_task_file` now reads `parent_task_id` first, falling back to `parent` for pre-fix fixtures/tasks. Both pinned regression tests un-ignored and pass against a real fixture repo + real CLI; new fast unit test `parses_parent_task_id_and_falls_back_to_the_old_parent_key` (backlog.rs) pins both keys without a CLI round trip. **Auditor's own test** (`sub_task_hierarchy_renders_correctly_from_a_real_cli_created_subtask`, `backlog_controls.rs`) goes further than either implementer test: real parent + two real subtasks via the real CLI (one marked Done), loaded through the real parser, driven through the actual List-lens GUI render — roll-up badge shows the correct real `[1/2]` count, tree expand/collapse reveals both real children, "+ Subtask" pre-fills the real parent id. This is the specific blind spot (GUI render path against real, not struct-constructed, data) that let the original defect ship undetected — now closed.

2. **MEDIUM — List lens can't sort by labels, assignee, or milestone.** `BacklogTaskSortKey` only has Triage/Task/Status/Priority/AcceptanceCriteria. The webview supports all of these plus labels/assignee/milestone. See parity matrix.
   - **RESOLVED, independently confirmed**: `BacklogTaskSortKey::{Labels,Assignee,Milestone}` added, wired into the List lens's sort combo. Implementer's tests prove the comparator; auditor's `sort_by_labels_actually_reorders_the_rendered_rows`/`sort_by_milestone_actually_reorders_the_rendered_rows` prove the comparator is actually wired into the rendered row order (via each row's on-screen vertical position), which the comparator-only unit tests couldn't have caught if the wiring itself were wrong.

3. **MEDIUM — no milestone or label filter in the List lens toolbar.** Milestone browsing requires switching to the separate Milestones lens; label filtering is only reachable through the general free-text filter, not a dedicated control. See parity matrix.
   - **RESOLVED, independently confirmed**: dedicated Milestone and Label filter combos added to the toolbar, wired into `SavedView`. Auditor's own 3-task fixture confirms both filters active *simultaneously* narrow correctly (the implementer's tests exercise one at a time), and a real save-to-disk-and-reload round trip confirms both filters persist through `SavedView`.

4. **LOW — Board cards omit labels and age.** The webview's kanban card shows id/priority/labels/age; Switchbard's board strip shows id/priority/AC-progress/blocked-marker/dispatch-pill but not labels or age.
   - **RESOLVED, independently confirmed**: labels (comma-joined) and a humanized age (`updated_date`, falling back to `created_date`) added to the strip. Auditor's own test specifically forces `created_date` and `updated_date` into different `humanize_age` buckets (40 days vs. 2 days) to prove the *precedence* claim, not just that some age renders.

5. **LOW — no "Clean Up Old Tasks" bulk action.** Nearest equivalent is per-task Archive, one at a time.
   - **NOT RESOLVED (fix wave 1) — implemented, but non-functional against the real CLI.** A confirm-gated, cross-repo "Clean Up Old Tasks" button was added, and the implementer's four tests all pass — but all four use an **in-memory fixture** (`archive_backlog_task` is never actually invoked against a real project in the fix wave's own test suite). Auditor's real-fixture test (`clean_up_old_tasks_confirm_archives_the_done_task_in_both_real_repos`, two real repos, real CLI) found that **the real `backlog` CLI v1.47.1 refuses `task archive` on a Done-status task**: `"Task TASK-1 is Done. Done tasks should be completed, not archived. Use: backlog task complete TASK-1"`. Since Clean Up Old Tasks exclusively targets Done tasks (`toolbar::cleanup_candidates` filters on `task.is_done()`), **every archive call it ever makes fails** — a 0% success rate against any real Backlog.md project. The failure is surfaced in the status line (`"cleaned up 0/N Done tasks...; first failure: ..."`), not silent, but the feature cannot accomplish its stated purpose even once. Likely fix: call `backlog task complete` instead of `backlog task archive` for Done tasks — which would also change the resulting `BacklogTaskSource` from `Archived` to `Completed`, a design decision for whoever picks this up, not this auditor's call. Test pinned and `#[ignore]`d: `clean_up_old_tasks_confirm_archives_the_done_task_in_both_real_repos` (`qa_reverify_2026_08_05.rs`).
   - **RESOLVED (fix wave 2), implementer-reported, pending independent re-verification.** `complete_backlog_task` added to core; `HiveApp::spawn_backlog_cleanup` now calls it instead of `archive_backlog_task`. The pinned regression test is un-ignored, its assertion updated `Archived`→`Completed` per its own anticipation of exactly this design decision, and reported passing against two real fixture repos.

6. **LOW — Create modal can't set labels/assignee/milestone/dependencies at creation time.** Must be added afterward via the detail pane.
   - **RESOLVED, independently confirmed**: all four fields added to the Create modal, flags verified against a real `backlog task create --help` before implementing. Auditor's test types real keystrokes into the real modal (not `state_mut()`) on a real fixture repo and reparses via the real CLI's own parser afterward — closing the one gap the implementer's own GUI test left open (their test set the buffers directly, never actually drove the fields' typing mechanics).

7. **HIGH — NEW, found during re-verification (not part of the original six): the single-task Archive button shares Defect 5's exact root cause.** `detail_lists::render_archive` has no status check before calling `archive_backlog_task`; against a real Done-status task, the real CLI rejects the call with the same `"...should be completed, not archived"` error Defect 5 hits. Every prior Archive test — in the original audit (`archive_moves_the_task_out_of_the_active_set`) and the fix wave alike — used a non-Done fixture task (`create_fixture_task`'s default status is "To Do"), so this was never exercised until now. Practical exposure is lower than Defect 5 (a user manually archiving one task at a time is less likely to hit a Done task than a feature that exclusively targets them, and the CLI's rejection does surface as a visible failure status, not data corruption), but it is the same class of correctness gap: a shipped, seemingly-working control that silently cannot complete its job for an entire category of real input. Ranked HIGH alongside Defect 1 because, like Defect 1, it's a *correctness* defect in already-shipped functionality, not a missing affordance. Test pinned and `#[ignore]`d: `archiving_a_done_task_is_rejected_by_the_real_cli` (`backlog_cli_mutations.rs`).
   - **RESOLVED (fix wave 2), implementer-reported, pending independent re-verification.** `detail_lists::render_archive` now switches on `task.is_done()`: a Done task shows "Complete" (routes through the new `complete_backlog_task`), a non-Done task keeps "Archive" unchanged — the detail pane no longer offers an action the CLI will reject. The pinned regression test is un-ignored, rewritten to pin both the CLI's permanent refusal of `archive` on a Done task and `complete_backlog_task`'s success (`BacklogTaskSource::Completed`), and reported passing. New GUI-level coverage: `done_task_offers_complete_instead_of_archive` (backlog_controls.rs).

None of the original six were regressions — every one was an additive gap against the webview, and none blocked the CLI-backed data model. Defects 1 and 7 are the only ones with a correctness impact (shipped functionality silently/audibly failing); 2, 3, 4, 6 were missing affordances now added; 5 is a missing affordance that was added but doesn't work.
