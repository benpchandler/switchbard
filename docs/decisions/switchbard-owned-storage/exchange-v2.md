# Current exchange wire format: version 2

This describes the implemented ExchangeSnapshot/ExchangeRecord/ExchangeContent types in crates/switchbard-core/src/storage/exchange.rs, causal-clock rules in exchange/clocks.rs and native candidate checks in backlog/storage_validation.rs. The JSON schema and example accompany those current shapes; historical exchange-v1 files are retired. This source-grounded document is not independent parser/golden-vector test evidence.

## Envelope

The six required fields, in canonical output order, are version, repo_id, epoch_id, kinds, records, digest. version is integer 2. UUID strings use lowercase canonical hyphenated form. kinds declares the complete set of centrally owned kinds in the snapshot, including empty kinds. Unknown compatible kind names are accepted and retained as opaque raw documents; native known-kind semantics are validated by the checked domain callback. Unknown outer fields reject. Per-record content_version is independent of the database schema and outer exchange version. It defaults to 1 and is omitted from canonical output at 1, preserving existing version 2 snapshot digests. Positive newer versions remain opaque; local commands refuse unsupported record mutation. Database schema 5 persists this metadata; unsupported newer database schemas refuse opening. Unknown outer semantics still reject rather than being ignored.

Each record contains, in output order: id, kind, locator, content, optional content_version, deleted, clock. id is stable RecordId; kind must appear in kinds. The generic envelope requires unique record IDs and unique (kind,locator) pairs, including tombstones. Native validation additionally checks task public IDs across lifecycles, hierarchy names and aggregate singleton locators. repo_id scopes the whole file. There are no machine paths, local revision numbers, process IDs, receipts or workspace-order fields in this envelope. User document prose is not redacted.

## Readable content

content is a closed tagged object with encoding and data. encoding=utf8-lines means data is an array of nonempty UTF-8 string fragments, each containing at most one LF at its end. Every fragment except the last must end with LF. Concatenation reconstructs exact document bytes. Empty payload is an empty array. CRLF, no final LF, Unicode, null characters inside document content and custom YAML/body text survive as decoded payload bytes. This representation makes each document line reviewable in a Git diff instead of replacing one opaque encoded paragraph.

encoding=base64 means data is standard padded base64 decoded by the product's STANDARD engine. It allows opaque non-UTF-8 data. The exporter chooses utf8-lines whenever stored bytes are valid UTF-8; accepted alternative input encodings may therefore normalize on export while preserving decoded bytes. Outer structure is strict, but the complete raw content remains flexible. Known native records must be supported UTF-8 Markdown/YAML; unknown kinds may remain opaque bytes. No typed model serialization replaces the raw document.

## Bounds and parser requirements

File size is at most 67,108,864 bytes. The snapshot carries at most 100,000 records and 128 declared kinds. Each decoded document is at most 4,194,304 bytes, and total decoded payload is at most 67,108,864 bytes. Kind and locator lengths are at most 128 and 4096 UTF-8 bytes respectively; schema maxLength counts code points, so product byte checks remain authoritative. Locators are nonempty and NUL-free; known native kinds additionally require exact confined directory/file patterns.

Clocks have 1 through 128 unique replica UUID keys; counters are positive integers through 9,007,199,254,740,991. Root selected 128 entries and JSON-safe counters for bounded cross-tool interoperability, replacing the earlier proposed 256-entry limit. No fractional, zero or overflowing counter can be accepted. New local mutation at a bound rejects rather than truncating or wrapping history. Explicit parser depth is limited to 32 nested object/array containers, ignoring braces/brackets inside quoted strings. These changes need the actual boundary tests bound in coverage-current.md, not merely schema validation.

Serde rejects duplicate/unknown struct fields; the causal-clock map uses a custom duplicate-key/entry-limit visitor. Native YAML is parsed without losing original bytes and malformed known fields reject through checked callbacks. JSON Schema cannot establish duplicate-key handling, exact lexical integer rules, resource allocation bounds, byte lengths, normalized UUID identity or complete native graph legality. Product parser tests must prove them.

## Canonical bytes and digest

Export sorts kinds lexically and records by id; clock maps use BTreeMap key order. It preserves Rust struct field order listed above, not alphabetical object-key sorting. Content fields are encoding then data. Canonical file output is serde_json pretty serialization with two-space indentation plus exactly one final LF. Within UTF-8 line fragments newlines are JSON escapes; decoded document line endings remain intact.

To compute digest, clone the snapshot, replace digest with the empty string, sort kinds and records, and serialize compact JSON using the same struct field order and clock key order. SHA-256 of those UTF-8 bytes becomes lowercase hex. There is no final LF in digest input. The digest includes version/repo/epoch/kinds/records and the empty digest member itself. It is a semantic snapshot digest, not an exact source-file-byte digest; equivalent external whitespace does not change it. The original acceptance's exact-byte preview invalidation remains separately tracked until implemented and tested.

exchange-v2.example.json is an illustrative fixed document assembled in this documented field order. Its digest was computed independently in Python. The real CLI test `independent_wire_golden_bootstraps_and_exports_identical_bytes` consumes it, binds a new repository, reads its initiative through the native interface, and exports identical bytes. This establishes one fixed cross-implementation fixture, not the entire boundary corpus. The former v1 digest/domain separator/base_records rules do not apply.

## Causal merge and CLI

Use exchange-current.md for per-record dominance, equal-clock integrity, concurrent merge/resolution, omission and tombstone rules. The product CLI exposes storage status, migrate, document, export, import, backup, restore and rebind. Export defaults to .switchbard/tasks.json and is explicit; identical bytes produce no changes. A lock plus compare-before-atomic-replace protects competing writers; independently changed content requires import/reconciliation or explicit --replace. Import is previewed and applies using the returned semantic snapshot digest and expected database sequence; --bind joins an explicitly unbound scope. CLI resolves local/incoming choices and accepts a reviewed --resolution-file for custom content or incoming relocation. Resolution files bind the same snapshot digest and database sequence as the apply flags. Preview reports native validation errors and candidate record IDs so independently allocated public-ID collisions can be corrected explicitly. Supported restore rotates replica identity. Epoch mismatch currently rejects; an explicit compaction command remains unimplemented.

Normal native edits remain central and do not auto-export or perform Git operations. Actual test bindings and remaining original acceptance gaps are listed in coverage-current.md. Real-data cutover, native client continuity and reporter acceptance remain separate from temporary peer fixtures.
