# Storage and exchange architecture

Proposed contract. Current source evidence is in discovery.md and blast-radius.json.

## Identity and raw records

RepositoryId and RecordId are opaque UUIDs. A registry maps Git common directories and local path aliases to RepositoryId. Linked worktrees resolve through their common Git directory. A moved repository needs explicit rebind when continuity cannot be proved. An independent clone explicitly binds the exchange file's RepositoryId. A fork gets a new identity unless the user deliberately joins the original scope. Matching names or remotes are insufficient.

Preserve support for non-Git backlog directories by explicit path binding to a minted RepositoryId. Such scopes have no common-Git identity and use explicit rebind on a move; exporting their single exchange file does not require Git. Git transport is optional for every scope.

Separate database identity from app tracking intent. The database alone owns RepositoryId, Git/path bindings, migration state and task records. Existing Config.repos remains the user's selected set of paths to scan/display; Config.worktrees remains user alias/display preference. Neither collection defines or deletes database identity. Removing a repo from app tracking hides it without deleting its records. Explicit database registration/rebind updates only database identity; obsolete path aliases remain resolvable until explicitly removed. Adding a tracked path updates Config and can resolve an existing binding, but cannot silently migrate or merge task scopes. A stale tracking path reports unavailable checkout while its known task scope remains accessible. UI commands that also update tracking preferences report a config-write failure separately and retry that preference write; they cannot roll back or fabricate a committed binding. If the DB cannot be opened, all database identity/task lookups fail explicitly, including for configured paths; the app must not guess from Config that a scope is safe to write as legacy. Legacy mode is chosen only after successfully reading the database registry and proving the scope is not migrated.

Records carry RepositoryId, RecordId, kind, revision, lifecycle, canonical raw payload, and provenance. Public locators are unique within (RepositoryId, kind, public_id); therefore task IDs/prefixes remain unique within a repository while a project may legitimately have the same locator text as a task. Parent changes retain RecordId even when display numbers change. Required internal links are scoped and bind stable IDs; external URL strings do not acquire invented semantics.

Legacy membership names may have no corresponding project/initiative definition. Preserve these as explicitly unresolved references with their original name and scope; do not manufacture definitions or reject lossless migration solely for an optional unresolved membership. A missing optional relationship means unknown, not deleted or invalid. Newly declared required links still validate against real scoped targets.

Workspace-wide cross-repo ordering moves from the hub overlay into database workspace scope with its exact existing order preserved. Per-repo rank belongs to the repository and is exchanged. Workspace-wide ordering remains local to the database and is not exported through a single repository's file; an import cannot reorder another repository. Unresolved legacy repo/task ordering locators remain explicit unresolved entries until bindings are established.

Known workspace-order entries resolve to RepositoryId plus RecordId during migration. Replace the current path/display-ID TriageEntry projection for resolved entries; retaining old locators for all entries is not central identity. Preserve only genuinely unresolved entries as opaque legacy locators. Rebinding a repo and reparenting a task must retain its exact order and cannot collide with another repo's matching display ID.

Imported task/project/initiative Markdown is stored byte-for-byte with revision history; derived typed fields are indexed transactionally. Reuse surgical edits as pure buffer transformations to preserve unknown frontmatter and body sections. Goals, rank and task config similarly preserve original YAML and derive typed data. Exchange embeds raw payload bytes as base64 inside its single JSON document. No companion raw files are required for collaboration.

Task configuration includes status vocabulary and configured task prefixes, including mutations exposed by backlog/status_config.rs. For migrated scopes, status/config reads and upgrades go through the same database command boundary; only unmigrated legacy mode may write backlog/config.yml. Migration and exchange retain original config bytes and typed vocabulary/prefix projections. Status changes validate against the central configuration revision, and config mutation participates in normal-edit no-Git-change and round-trip tests.

Configuration has one logical role: at most one kind=config record per repository, with public_id=task-config, active lifecycle and no tombstone. When absent, configured statuses are an empty list and the prefix is TASK, matching the existing parser defaults; ordinary display still uses the standard status vocabulary. A reset writes an explicit default payload rather than deleting config. Migration inventories backlog/config.yml, .backlog/config.yml and backlog.config.yml in the existing status-config precedence order, preserving every source in the protected manifest/backup. Because today's general reader reads only backlog/config.yml while status upgrades can choose an alternate path, any alternate-only source or divergent worktree config requires a previewed effective-config decision. Do not silently choose a new vocabulary. The selected canonical payload becomes the one config record; unselected originals remain recoverable provenance, not competing live or exchange configs. Fresh imports therefore have one deterministic effective vocabulary/prefix without source paths.

Once an exchange base contains task-config, its current snapshot must retain that same config RecordId. Reject config omission or replacement identity across base/current; reset changes the payload in place. This continuity rule complements singleton validation and prevents a collaborator bootstrap from interpreting a dropped configuration as new defaults.

## Database commands and visibility

One SQLite database owns repository bindings, canonical records/revisions, relationships, exchange checkpoints, migration manifests/source digests, command receipts, conflict plans and a monotonic change sequence. Machine filesystem permissions are the access boundary. Imported JSON is data, never executable configuration.

Create database files, SQLite sidecars and backup files with owner-only read/write permissions (0600 on supported Unix platforms), and new backup directories with 0700. Validate sensitive file ownership/permissions before use and fail with a repair instruction if privacy cannot be established. Do not broadly chmod the user's existing ~/.switchbard directory or arbitrary backup destinations. Test creation under a permissive umask and reject symlink/foreign-owned sensitive file substitution; user-selected exchange files intentionally follow repository collaboration permissions. Receipts and raw migration provenance remain inside the protected database/backup boundary.

Each mutation takes command_id and expected revision. A transaction validates scope, lifecycle and links; changes payload, indices, related records and change sequence; and records the receipt. Identical replay returns the original result; reuse of an ID with different arguments rejects. Database constraints enforce unique identities and links. Busy handling is bounded to five seconds and reports an actionable retry. Multiple processes use this module; no single GUI process owns availability.

CLI reads see committed changes on the next read. Active GUI/TUI instances check the change sequence at most once per second and refresh cached projections off the input/render thread. Acceptance requires visibility within two seconds. Refocus refreshes before enabling writes. Editor drafts retain expected revisions and surface concurrent-edit conflicts without discarding drafts.

Runtime task keys, selection, pending drafts, write locks, task dispatch maps, and task snapshot caches use RepositoryId plus RecordId for migrated scopes. In particular, replace the GUI's path/display-ID BacklogTaskKey and path-keyed task cache; do not limit central identity to the SQL layer. Retain separate filesystem locators for process execution and Git observations. Stable-key tests must rename/rebind a repo and reparent a task while selected and while a draft is pending, proving that selection and the eventual write still refer to the same RecordId. Legacy runtime adapters remain scoped and cannot collide with central keys.

## One-file format v1

The optional path is .switchbard/tasks.json. The envelope contains version, RepositoryId, semantic snapshot digest, optional base digest and complete base records, plus current records including tombstones. Arrays sort by RecordId and keys have canonical ordering. Digests cover semantic content excluding the digest field. No machine paths, process IDs, executable views, app secrets, or xplan state enter the exchange. User task prose is collaboration content and is not silently redacted.

Export captures a consistent database read snapshot. Repeated export with unchanged content/base emits identical bytes; no fresh wall-clock timestamp changes it. Write a sibling temp file then atomically replace the target. Record the checkpoint only after replacement; ambiguous outcomes reconcile by digest. Refuse to overwrite independently modified exchange content until it is imported/reconciled or explicitly replaced. Dirty Git state alone is not a blocker.

First export contains the complete repository state with no base. Later export uses the last accepted or explicitly exported snapshot as base, embeds that base's full records and digest, and retains the checkpoint in the database. Repeated export of the same current content reuses the existing envelope rather than advancing the base. At most one base and one current snapshot are embedded, not unbounded history.

A populated repo accepts a base only if its verified digest matches a retained local checkpoint. Unknown bases require explicit reconciliation. A fresh empty, explicitly bound repo can bootstrap from a complete valid snapshot without a known base. Bootstrap stores that snapshot as a checkpoint; it cannot overwrite existing records. A base transmitted in an untrusted file is not evidence of local acceptance.

Bound input to 64 MiB total, 100,000 records, 4 MiB decoded payload per record, and nesting depth 32. Reject unsupported versions, oversize data, mismatched counts, invalid IDs/links and bad digests before any write. Never truncate or partially import. These proposed v1 compatibility limits need boundary tests.

The 100,000 record limit counts base plus current records together. Reject duplicate JSON object keys at every nesting level before typed deserialization, rather than accepting whichever key appears last. The normative exchange-v1.md, exchange-v1.schema.json and golden vectors define exact field shapes, SHA-256 digest input, JSON escaping/order and base64 encoding. Product parser/export tests must match those independent bytes/digests; a round trip through only the same implementation is insufficient interoperability evidence.

## Merge, preview and apply

For each record compare semantic base B, local L and incoming I: L=I is a no-op; L=B takes I; I=B keeps L; otherwise conflict. Distinct-record edits merge. Incoming absence keeps L. Explicit tombstone versus local edit conflicts. Different RecordIds with the same RepositoryId, kind and public_id conflict; matching public_id text across different kinds is legal. Validate the complete merged graph, including uniqueness, required references, lifecycle and cycles, before applying anything.

Preview stores a bounded plan with source digest and expected repo revision. Apply rechecks both; concurrent database edits or source-file changes invalidate the plan and require new preview. Commit all records, provenance/checkpoint and receipt in one transaction. A conflict changes no live records. Resolution can choose local, incoming or custom content, then revalidates the whole candidate. Retain originals for recovery; timestamps never decide which human input survives.

The normal collaborator workflow is import, edit through Switchbard, export, PR the file. Git conflict markers and manually edited stale digests reject with an actionable validate/canonicalize instruction. A canonicalization command may recompute format/digests but never implies import approval or makes an unknown base trusted.

## Migration and recovery

Migrate explicitly per repo into the shared database. Inventory active/completed/draft/archive records, hierarchy, goals, rank/config, sibling worktrees, and active branches covered by today's allocator. Preserve bytes plus Git/path/digest provenance in a recoverable backup and manifest. Identical copies collapse; divergent same-ID copies need explicit reconciliation. Unmerged branch records cannot silently become authoritative. Recheck all source digests at apply; changing inputs invalidate preview.

Quiesce known legacy writers before cutover. Updated clients recognize central bindings and never write legacy records. Old binaries remain unsupported; a new marker cannot make old code aware of the database. Preserve files until explicit cleanup and report later legacy divergence without automatic import. Do not claim to prevent arbitrary text editors or old clients from changing their filesystem copies.

Prepare backups before transactionally importing and activating central authority. Failure leaves legacy mode active. After cutover, copying old files or reverting code loses newer work and is not rollback. Provide a database-consistent backup and test restore in a temporary store. Reverse migration requires a lossless export/reconciliation of post-cutover changes. A per-repo exchange omits other repos, receipts and machine state and is not disaster recovery.

## Consumer conservation

Registered repos work without backlog directories. CLI path/display-ID selection remains compatible. Refine receives a versioned raw-document view or temporary read-only document and applies centrally. Dispatch keeps execution worktree paths separately from stable task identity. Queue and orchestrator protocol semantics remain coherent. Worktree removal cannot delete task truth. GitHub observations, xplan missions, process liveness and service lifecycle retain their own authority.

New dispatch runs use a collision-resistant RunId bound to RepositoryId and RecordId. Namespace log, prompt, pid sidecar and inspection/history records by this identity, never display ID plus second alone in a global temporary directory. Keep execution paths separate. Legacy run artifacts remain readable only when their original scope can be established; ambiguous historical attribution is explicitly unverifiable and cannot supply a kill handle. Concurrent dispatches of TASK-1 from two repositories in the same second must have distinct artifacts and scope-correct inspection and authenticated kill behavior. This preserves the existing fail-closed kill policy while removing display-ID collisions from the new contract.
